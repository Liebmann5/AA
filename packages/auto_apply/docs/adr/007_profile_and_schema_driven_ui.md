# ADR‑007: Pydantic Schema‑Driven User Interface

**Status:** Accepted  
**Date:** 2025‑12‑04  
**Deciders:** Nick Liebmann  
**Technical Story:** Before the schema‑driven approach, every UI component that allowed the user to edit their profile maintained its own hardcoded list of field names, labels, and option values. Adding a new `WorkplaceType` or `EmploymentType` required updating both the GUI settings editor and the CLI wizard — and often produced label inconsistencies that caused silent data loss. The user interface needed a single source of truth for field metadata.

---

## Context

AutoApply’s `UserProfile` is a deeply nested Pydantic model with many controlled vocabularies (`WorkplaceType`, `EmploymentType`, `Gender`, `Race`, `VeteranStatus`, etc.). Two primary adapters — the GUI settings editor and the CLI wizard — allow users to view and edit their profile.

Before this ADR, both adapters maintained independent, hardcoded lists of:

- Which fields to display
- What label to show for each field
- What options to present for dropdowns and checkboxes
- What default value to pre‑fill

This created three concrete problems:

1.  **Drift.** When a new `WorkplaceType` was added to the domain model, the GUI and CLI did not pick it up. It had to be added manually in multiple files, and forgetting one created a silent inconsistency.
2.  **Label inconsistency.** The GUI might say “In‑Office” while the model stored `"in-office"`. Mismatches caused data loss on save because the UI wrote a value the model could not parse.
3.  **No localisation.** All labels were hardcoded in English. The i18n service (`application/services/i18n.py`) existed but was not consumed by the settings UI.

---

## Decision

The `UserProfile` Pydantic model is the single source of truth for all field metadata. A shared service, `build_ui_schema()`, walks `UserProfile.model_json_schema()` and produces a flat list of `UIField` descriptors. Both the GUI settings editor and the CLI wizard consume these descriptors. Adding a new field to the model automatically propagates to every user interface with zero UI code changes.

### UIField Descriptor

```python
@dataclass(frozen=True)
class UIField:
    key: str           # dot‑separated path, e.g. "search_preferences.workplace_types"
    label: str         # i18n‑resolved human‑readable label
    help: str          # from Field(description=…)
    kind: FieldKind    # "text" | "number" | "select" | "multiselect" | "path" | "bool" | "email" | "url"
    options: tuple[str, ...] | None  # for select/multiselect, derived from Literal/enum
    min: float | None
    max: float | None
    required: bool
```

### How `build_ui_schema()` Works

1.  Calls `profile_cls.model_json_schema()` to get the JSON Schema for the entire `UserProfile`.
2.  Recursively walks all properties, following `$ref` pointers into `$defs`.
3.  For each leaf field, classifies the `kind` based on schema type, enum values, format, and naming conventions:

    | Schema indicator | Kind |
    | ---------------- | ---- |
    | `string` with `enum` | `select` |
    | `array` with `enum` items | `multiselect` |
    | `boolean` | `bool` |
    | `integer` / `number` | `number` |
    | field name in `_PATH_FIELD_NAMES` | `path` |
    | field name in `_URL_FIELD_NAMES` or `format=uri` | `url` |
    | `format=email` | `email` |

4.  Resolves the label by first checking i18n translation keys, then falling back to the schema’s `title` or a snake‑case‑to‑title conversion.
5.  Extracts `description`, `minimum`/`maximum`, and `required` status from the schema.

### GUI Settings Editor Integration

The settings editor stores the `UIField` list at construction time. It uses `_schema_field(key)` to look up the descriptor for a given profile path. Checkbox lists for workplace types and employment types are generated by iterating `UIField.options` — adding a new enum member automatically creates a new checkbox.

On save, the editor reads the checkbox states back and writes the exact enum strings from `UIField.options` into the Pydantic model, guaranteeing no label‑to‑value mismatch.

Admin‑locked fields are detected via `AdminPolicy.is_field_locked()` and rendered as disabled with a lock icon (🔒). Locked fields are skipped during save, preserving the user’s base preference.

### CLI Wizard Integration

The `CLIWizard` uses `build_ui_schema()` for two purposes:

1.  Resolving human‑readable prompt labels via `_schema_label(key, fallback)`.
2.  Deriving default values from the user’s existing profile when available (e.g. pre‑filling the job titles prompt with the user’s `desired_job_titles`).

If the schema is unavailable (e.g. import error), `_schema_label()` returns the hardcoded fallback string, ensuring the wizard still functions.

### Internationalisation Integration

Before falling back to the schema title, `build_ui_schema()` attempts i18n resolution:

```python
def _try_get_text(key: str) -> str | None:
    for ns in ("wizard", "settings", "profile", "gui"):
        full_key = f"{ns}.field_{key}"
        result = get_text(full_key)
        if result != full_key:   # get_text returns the key itself on miss
            return result
    return None
```

Translation keys like `"settings.field_desired_job_titles"` in `es.json` produce Spanish labels in the settings editor when the user’s locale is Spanish. The inline `LANG_EN`/`LANG_ES` dicts previously in `gui/strings.py` have been deleted; all string resolution routes through the i18n service.

## Options Considered

### Keep hardcoded field lists in each UI component
**Rejected.** This was the status quo and the source of the drift and inconsistency problems. It also made i18n impossible without duplicating every label.

### Use a separate UI schema file (JSON/YAML) maintained manually
**Rejected.** A manually maintained UI schema would drift from the Pydantic model just as the hardcoded lists did. The model is the source of truth for validation; duplicating its structure in another file is a maintenance burden.

### Generate the UI schema from the Pydantic model at build time and commit the output
**Rejected.** This would work but adds a build step. Generating it at runtime from the live model guarantees it is always in sync with the installed version.

---

## Consequences

### What becomes easier

- **Adding a profile field:** Add the field to the Pydantic model. Add an optional i18n key if a custom label is desired. Restart. Both GUI and CLI automatically include the new field.
- **Adding an enum member:** Add the member to the `Literal` type or Enum. It appears as a checkbox or dropdown option automatically.
- **Localisation:** Translating the UI for a new language requires only a new `locales/<lang>.json` file. No code changes.
- **Admin policy enforcement:** The settings editor queries `AdminPolicy.is_field_locked()` per field and disables locked controls. No per‑field UI logic is needed.

### What becomes harder

- **Custom UI logic per field:** If a field needs a non‑standard widget (e.g. a colour picker, a date range), the generic `UIField` descriptor may not suffice. Such cases require a manual override in the UI component, which must be maintained alongside the schema.
- **Schema walking performance:** `model_json_schema()` is called once at component construction and produces a moderately large dict. On very low‑resource machines, this adds a small startup cost. It is acceptable because it replaces multiple hardcoded lists and manual field lookups.

---

## JSON Resume Import/Export

The profile schema is AA‑specific and richer than the JSON Resume standard. A planned `application/services/json_resume_io.py` module will provide two‑way mapping between `UserProfile` and the JSON Resume format.

Key design decision: the internal schema remains `UserProfile` at all times. JSON Resume is an I/O format, not an internal representation. Fields without a JSON Resume analog (politeness settings, search preferences, EEO info, app_config) are preserved in AA’s internal storage and simply absent from the exported JSON Resume.

This means a user can import a JSON Resume to populate their profile, export a JSON Resume to share with career services, and their AA‑specific settings are never lost in the round‑trip.
